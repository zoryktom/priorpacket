# Research Protocol and Benchmark Methodology

**Status:** synthetic-data research artifact. Not clinical, payer, or coverage guidance. No real PHI.

## Question
Does a deterministic, policy-driven evidence engine reliably distinguish packets that are ready, incomplete, ambiguous, mismatched, or invalid, without ever reporting READY when evidence is missing or contradicted?

## Outcomes
`INVALID_INPUT` > `POLICY_MISMATCH` > `INCOMPLETE` > `NEEDS_REVIEW` > `READY` (precedence, highest first).
Absence of evidence in a record is never treated as proof that the clinical fact is absent; it is reported as missing evidence.

## Benchmark (`benchmark/v1`)
45 hand-authored synthetic cases, two workflows (knee MRI `73721`; diabetes CGM `E2103`), categories: A positive (7), B missing (14), C review (9), D invalid (8), E mismatch (5), F robustness (2). Cases are generated by `scripts/generate_benchmark.py` (`--check` verifies committed files are current).

Expected values were authored by the developer and, for 11 issue-code expectations, adjudicated to the engine's more specific code (e.g. `EVIDENCE_OUTSIDE_WINDOW`, `VALUE_OUT_OF_RANGE`). The benchmark is therefore a regression and specification suite, not independent validation; the same author wrote engine and truth labels.

## Metrics
All ratios report numerator/denominator; undefined ratios are `null`. Outcome accuracy, per-class precision/recall/F1, false-READY rate (READY predicted when expected is not READY, over non-READY cases), missing-criteria precision/recall, evidence traceability (met criteria with resource provenance), risk-band and issue-code agreement.

## Counterfactual checks
35 single-edit perturbations of two READY cases (remove evidence, shift dates, change units, wrong patient, etc.) assert a documented invariant (e.g. removing mandatory evidence can never yield READY).

## Reproduce
```bash
pip install -e ".[dev]"
pytest
priorpacket benchmark --out reports/benchmark
priorpacket reproduce      # compares to benchmark/v1/reference_metrics.json
```
Outputs include `SHA256SUMS` and `environment.json`. The result digest includes the engine version; regenerate the reference with `priorpacket benchmark --write-reference` after a version bump.

## Policy semantics notes
- Look-back windows and effective dates are inclusive.
- `MISSING_EVIDENCE` is emitted only when no candidate was rejected; otherwise the rejection code is reported.
- Risk band is `moderate` when completion rate ≥ 0.67 else `high` for INCOMPLETE/NEEDS_REVIEW; 2 of 3 (0.667) is therefore `high` (inherited legacy behaviour).
- Policy fields: `schema_version`, `policy_version`, `status`, `effective_start/end`, per-criterion `required`, `code_systems`, `conflict_keywords`, `unit`/`unit_aliases`, `prerequisite`, `min_value`/`max_value`. Unknown keys are errors.

## Security and privacy
Local-first; no external calls. The server binds loopback by default; the Dockerfile binds 0.0.0.0 because containers require it (publish the port to localhost only). Rendered HTML escapes untrusted text.

## Limitations
Synthetic data only; simplified code-system handling; `validate-fhir` is a lightweight layered check and does **not** replace the HL7 FHIR Validator or PAS profile validation; single-author labels; no evaluation on real-world payer policies.
